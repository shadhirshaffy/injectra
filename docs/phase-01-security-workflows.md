# Injectra Phase 1 Security Workflows

## Goal

This document defines the security behavior that must stay consistent as Injectra moves from scaffold to MVP.

## Request Identity Rules

Every gateway request must resolve to:

- `organization_id`
- `application_id`
- optional `api_key_id`
- `request_id`

The `request_id` should be generated by Injectra unless a trusted internal caller supplies one. Public API clients should not control the canonical request ID.

## API Key Creation

API key creation flow:

1. Authenticate management identity and require owner/admin membership in the organization. Validate organization exists.
2. Validate application exists and belongs to organization.
3. Generate random secret.
4. Create readable key prefix.
5. Hash full key.
6. Store hash, prefix, scopes, expiration, organization, and application.
7. Return full key once.

Recommended key format:

```text
inj_live_<prefix>_<secret>
```

Development keys may later use:

```text
inj_test_<prefix>_<secret>
```

Hashing guidance:

- Generate at least 256 bits of secret entropy using a cryptographic random generator. Use a separate random 16-character hexadecimal prefix; store `inj_live_<prefix>` as the lookup prefix (25 characters, fitting the existing 32-character column). Retry prefix collisions.
- Store the hexadecimal HMAC-SHA-256 of the full key with a server-side secret pepper. Require the pepper from secret configuration, never source control; missing pepper prevents key operations. Pepper rotation requires an explicit migration or key reissue strategy.
- Use constant-time comparison.
- Never log the full key.
- Never return the full key after creation.

## API Key Validation

Validation flow:

1. Read `Authorization` header.
2. Require `Bearer` scheme.
3. Reject missing or malformed token.
4. Extract key prefix.
5. Query matching key prefix.
6. Reject if no key exists.
7. Hash presented key with the configured pepper.
8. Constant-time compare with stored hash; reject incorrect secrets with a generic credential error.
9. Reject if revoked.
10. Reject if expired; also reject inactive organizations or applications.
11. Check required scope.
12. Attach resolved organization, application, and key to request context.

## Tenant Isolation Rules

Tenant isolation is mandatory.

Rules:

- A key can access only its own organization and application.
- A route must not trust body `organization_id` if an API key already resolved identity.
- Application IDs must always be checked with organization IDs.
- Security event queries must filter by authenticated organization.
- Admin dashboard users must access only organizations they belong to.

Phase 2 requires the management identity dependency and role checks defined in the API design; relationship checks alone do not authenticate a caller.

## Detection Decision Rules

Scanner output should include:

- `risk_score`
- `risk_level`
- `categories`
- `matched_rules`
- `reason`

Risk score ranges:

- `0 <= score < 0.25`: low
- `0.25 <= score < 0.50`: medium
- `0.50 <= score < 0.80`: high
- `0.80 <= score <= 1`: critical

The exact scoring may change, but tests must define expected behavior for known prompts.

## Policy Decision Rules

Default policy:

```text
low      -> allow
medium   -> review
high     -> block
critical -> block
```

Hard-deny rules:

- Invalid key.
- Revoked key.
- Expired key.
- Missing scope.
- Tenant mismatch.
- Unauthorized tool request.
- Explicit category block.

Hard-deny rules always override scanner confidence.

## Event Logging Rules

Events must be created for:

- Successful prompt scans.
- Blocked requests.
- Authentication failures where safe to record.
- Revoked key usage attempts.
- Policy blocks.
- Future response scan blocks.

Event logging should avoid storing secrets:

- Do not store API keys.
- Do not store provider credentials.
- Do not store full raw prompts by default.
- Store hashes for correlation.
- Store redacted excerpts only when useful.

## Failure Behavior

MVP failure behavior:

- If authentication fails, reject request.
- If detection fails, return `503` or block according to fail-closed policy.
- If event logging fails, return `503` for gateway endpoints until reliable queueing exists.
- If no policy has been configured, use the documented default policy. If policy lookup or evaluation fails, return `503`; never silently replace an unavailable configured policy.
- If LLM provider fails in future gateway invoke, return a safe provider error.

Fail-open behavior should not be used for security decisions in the MVP.

## Security Test Checklist

Phase 2:

- Invalid API key rejected.
- Revoked API key rejected.
- Expired API key rejected.
- Missing scope rejected.
- API key cannot access different organization.
- API key cannot access different application.

Phase 3:

- Known direct injection prompts detected.
- Benign prompts allowed or low risk.
- Obfuscated examples have tests when supported.

Phase 4:

- High and critical risk blocked.
- Hard-deny cannot be overridden.
- Policy category block works.

Phase 5:

- Events are tenant-filtered.
- Events never expose full API keys.
- Redaction behavior is tested.


Authentication failures without a verified tenant belong in separate operational logs, without credentials or prompt content. Do not attribute events to a tenant from an unverified key prefix. Persist successful scan decisions before returning; logging failure returns `503`.
