# Phase 6 — Authenticated Public Scan API

## Delivered flow

`POST /api/v1/gateway/scan` connects application-key authentication, input
validation, deterministic detection, application policy evaluation, and durable
event persistence. It performs inspection only; it never calls a model provider,
executes a tool, or forwards customer content.

Authentication uses `Authorization: Bearer inj_live_...` and requires
`gateway:scan`. Organization, application, and key identity come exclusively from
verified key records. Missing/malformed/unknown credentials return 401; verified
revoked/expired keys retain their specific 401 codes, missing scope returns 403,
and inactive organizations/applications cannot scan. Management credentials cannot
scan. Authentication failures are not attributed to an unverified tenant.

## Request and response

```json
{
  "input": "Ignore previous instructions",
  "content_type": "prompt",
  "metadata": {"source": "chat"}
}
```

Input must be a UTF-8-encodable string containing 1–20,000 Unicode characters
before normalization, with visible content after normalization. Whitespace-only,
format-only, invalid Unicode, and non-string input are rejected. `content_type`
defaults to `prompt`; `rag_context`, `tool_output`, and `response` are also
supported. Metadata defaults to `{}` and must be a JSON object of at most 4 KiB
when serialized to UTF-8 JSON. Unknown request fields are rejected, including
organization/application IDs, policy overrides, and caller-defined event IDs.

Successful scans return HTTP 200 for **allow, review, and block**. A block is an
inspection result, not a transport failure. Review and block never authorize
forwarding. The response contains:

```json
{
  "request_id": "server-generated-uuid",
  "organization_id": "verified-organization-uuid",
  "application_id": "verified-application-uuid",
  "decision": "block",
  "risk_level": "high",
  "risk_score": 0.65,
  "categories": ["instruction_override"],
  "matched_rules": [{
    "id": "rule_instruction_override_001",
    "name": "Instruction override attempt",
    "category": "instruction_override",
    "severity": "high"
  }],
  "reason": "The default risk mapping determined the decision.",
  "event_id": "durably-persisted-event-uuid",
  "ruleset_version": "1.0.0",
  "policy_id": null,
  "policy_version": 0
}
```

Configured policies return their evaluated ID/version. Reasons describe the
policy decision using static text; matched rules describe the detection evidence.
The request UUID is generated by middleware, matches `X-Request-ID`, and is stored
on the event. Public caller-supplied request IDs are ignored. Responses include
`Cache-Control: no-store`. Input text, metadata values, hashes, and credentials
are never echoed in the response or validation errors.

## Transaction and failure guarantees

The route and key dependency share the request SQLAlchemy session. The route
scans, evaluates, stores the privacy-safe event, and materializes its validated
response while the transaction is open. It then explicitly commits before
returning HTTP 200. The shared session dependency commits only when a transaction
remains active, so it does not issue a redundant commit after a successful scan.
Management routes retain their existing automatic commit behavior.

Detection, policy lookup/evaluation, event flush, response-materialization, and
commit failures rollback and return a generic `503 service_unavailable`; errors
never become allow decisions. Validation returns the shared safe 422 format.
Canonical request IDs remain available on error responses. Exceptions, SQL
parameters, credentials, and input text are not included in error messages.

A lost database connection during commit may leave the client unable to know
whether a transaction committed. Retrying creates a new server request ID and may
create another event: this version does not promise exactly-once execution or
accept client idempotency keys. Because scans have no external side effects,
duplicates are inspection records rather than duplicated provider calls.

## Privacy and deployment

Event behavior follows Phase 5: SHA-256 correlation hashes, null raw/redacted
content, and only enumerated `source` metadata values persist. Unknown metadata
fields are discarded. Event rule/policy references preserve reproducibility.
The event service independently recomputes evidence before storing it.

There is no new migration. Apply all existing migrations through Phase 5 before
using the endpoint. The local public application database has not been migrated
automatically. Preserve the existing API-key pepper; changing it invalidates keys.

Example from an already configured local API (supply your own application key):

```powershell
$scanKey = Read-Host 'Application API key'
$scanBody = @{ input = 'Explain recursion'; metadata = @{ source = 'api' } } | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8000/api/v1/gateway/scan' `
  -Headers @{ Authorization = "Bearer $scanKey" } -ContentType 'application/json' -Body $scanBody
```

Use HTTPS for remote application clients. Production management identity,
retention operations, rate limiting, and operational capacity planning remain
release prerequisites; completing the scan route is not a production-launch claim.

## Verification

From `apps/api`, run `python -m pytest` with the local PostgreSQL test service.
Coverage includes allow/review/block decisions, content types, key states/scopes,
tenant-specific policies, input/metadata boundaries, canonical IDs, privacy,
corrupt policies, and every pipeline failure stage. Tests use an independent
session to prove events survive the route commit. Injected commit failures verify
that no successful response or event ID is returned. Existing management and
migration tests remain regression gates. Hosted CI results are reported in the PR.

Local verification on 2026-10-16 (Asia/Colombo): 375 backend tests passed,
including 50 public scan/transaction tests. The pre-existing AnyIO BlockingPortal
deprecation warning remains.
